# GMC-MPNN BBB Phase-1 geometry and GGL preprocessing plan

## Scope and fixed data contract

This document specifies the geometry and geometric graph learning (GGL) preprocessing contract for
the descriptor-free Phase-1 `BBB_Martins` experiment. It is an inspection and design record, not an
implementation. The existing leakage-controlled development split is fixed and must not be
redesigned: train has 1,561 molecules (1,187 positive and 374 negative), validation has 196
molecules (150 positive and 46 negative), and their exact canonical-SMILES and Murcko-scaffold
overlaps are both zero. The GMC and Chemprop validation memberships match exactly. The verified
manifest hashes and canonical-SMILES checks passed.

No old BBB test artifact may be resolved or opened by this pipeline. Geometry and GGL processing are
label-independent; all preprocessing settings are fixed without looking at validation labels. Only
the GGL scaler is data-fitted, and it is fitted to training atoms alone. No global RDKit descriptor
branch is part of Phase 1.

The source target for this inspection is the public GMC-MPNN repository at revision
[`ae080431950832be43e51f7cd9b0f7d4203e2267`](https://github.com/MathIntelligence/GMC-MPNN-BBBP/tree/ae080431950832be43e51f7cd9b0f7d4203e2267).
That repository has no explicit license. Its behavior may be independently reimplemented from this
specification, but source files must not be copied or vendored.

## Actual public structure-to-feature path

The released path is narrower than the paper suggests:

1. A separate, undocumented process produces one MOL2 file named from each CSV `id`.
2. `utils/get_ggl_ligand_features.py` reads the CSV in row order, chooses one row from
   `utils/kernels.csv`, and opens `<data_folder>/<id>.mol2`. The CSV SMILES is read but is not used
   to construct or verify the structure.
3. [`PandasMol2`](https://biopandas.github.io/biopandas/api_subpackages/biopandas.mol2/) reads the
   MOL2 atom table. The code consumes `atom_id`, `atom_type`, `x`, `y`, and `z`; it does not read the
   MOL2 bond table for GGL.
4. Atom rows whose `atom_type` is exactly `H` are removed. The remaining row order is retained.
5. Euclidean distances and radius-scaled kernel weights are calculated for every ordered pair of
   remaining rows.
6. Six row summaries are emitted in the order `minimum`, `maximum`, `sum`, `mean`, `median`,
   `standard_deviation`.
7. One array per CSV row is saved under positional NPZ keys such as `arr_0`. The archive carries no
   molecular identity, atom map, geometry provenance, or feature metadata.

The GGL generator therefore consumes MOL2 exclusively. The public training scripts consume only
the already generated NPZ arrays and do not require MOL2, BioPandas, OMEGA, OpenBabel, or a geometry
engine at training time.

### MOL2, hydrogens, types, charges, and fragments

- Hydrogens do not have to be present in the input MOL2 for the calculation to run. They are useful
  during conformer generation and force-field optimization, and the released parser removes them
  only after the MOL2 is read. The filter recognizes only the exact type string `H`; a differently
  typed hydrogen is unsupported rather than safely removed.
- SYBYL atom types are not generated by the GGL source. They must already be present in the MOL2.
  The 45-entry radius table includes differentiated types such as `C.ar`, `N.am`, `N.pl3`, `N.4`,
  and `O.co2`. Aromaticity, amide character, and charged local environments influence GGL only
  through these externally assigned type strings.
- Bond types, including aromatic bonds, are not read by the GGL calculation. They remain important
  upstream of it because a MOL2 writer/type engine needs correct bond perception to assign SYBYL
  atom types.
- Neither formal charge nor the MOL2 partial-charge column is used directly. Charge can affect a
  SYBYL type (for example `N.4` or `O.co2`) but is otherwise invisible to GGL.
- Disconnected fragments are not detected or separated. Every supported heavy-atom row contributes
  by Euclidean distance, including atoms in different fragments. Arbitrary relative placement of
  disconnected fragments would therefore create arbitrary features.
- Supported metals are handled only when their exact type appears in the radius table. Unsupported
  types produce `NaN` pair radii; the source prints a warning and its NaN-aware summaries omit those
  pairs. This can silently reduce or erase an atom's signal. Our Phase-1 adapter must instead flag
  unsupported types as blocking failures while retaining a source-faithful numerical function for
  golden tests.

MOL2 coordinates conventionally use Angstroms, and the fixed cutoff is interpreted as 12.0
Angstrom. The source does not declare or convert units, so an artifact must explicitly assert its
coordinate unit.

## Exact released six-feature calculation

Let the retained heavy atoms be indexed in MOL2 atom-table row order. For atoms `i` and `j`, let
`d_ij` be their Euclidean distance in Angstrom, `r_i` and `r_j` their source-table radii,
`R_ij = r_i + r_j`, `tau` the kernel scale, and `kappa` the kernel power. A selected kernel produces
one weight matrix:

```text
exponential: w_ij = exp(-(d_ij / (tau * R_ij)) ** kappa)
Lorentz:     w_ij = 1 / (1 + (d_ij / (tau * R_ij)) ** kappa)
```

The kernel grid contains 1,600 configurations: both kernel families, `tau` from 0.5 through 10.0 in
0.5 increments, and `kappa` from 0.5 through 20.0 in 0.5 increments. Kernel indexing in the public
feature script is user-facing one-based indexing converted to a zero-based CSV row. The released
BBBP training path has no universal kernel: its test harness hard-codes seed-specific choices, and
their selection provenance is not reproducible. The paper supplement reports an overall BBBP
setting of exponential, `tau=0.5`, `kappa=17.0`; this is evidence for a predeclared baseline setting,
not permission to tune against the old test.

Before summarization, the source sets self-interactions to NaN, rejects distances strictly greater
than 12.0 Angstrom, and applies this exact additional mask:

```text
reject(i, j) when d_ij >= sum_j(R_ij)
```

That expression is a row sum over all pair radii, not a bond-adjacency test and not the more natural
pairwise comparison `d_ij >= R_ij`. It usually supplies a large threshold and removes few pairs.
Although this looks like a defect relative to the paper's covalent-exclusion description, Phase 1
must reproduce it exactly. A corrected mask would be a separately named, post-baseline experiment.

For each atom `i`, let `S_i` contain every supported, non-self weight that survives both masks. The
six columns are:

| Column | Exact definition | Empty/all-NaN behavior |
|---|---|---|
| `ggl_min` | `min(S_i)` | NaN |
| `ggl_max` | `max(S_i)` | NaN |
| `ggl_sum` | `sum(S_i)` | 0 |
| `ggl_mean` | arithmetic mean of `S_i` | NaN |
| `ggl_median` | median of `S_i` | NaN |
| `ggl_std` | population standard deviation of `S_i` (`ddof=0`) | NaN |

All six columns use the same selected kernel, the same all-supported-heavy-atom subset, and the same
cutoff. Atom typing changes the radius scale and whether a pair is supported; it does not create
separate output channels. Pairwise distances make these values invariant to rigid translation,
rotation, and reflection, but not to conformer choice or atom typing. Chemprop 2.1.0 subsequently
replaces NaN entries in `V_f` with zero. The raw artifact must preserve and report the pre-fill
condition so a zero cannot conceal an unsupported type.

For Phase 1, the geometry/GGL implementation must accept the kernel type, `tau`, `kappa`, and cutoff
as resolved configuration. The seed-13 pilot should use the predeclared supplement setting
(exponential, `tau=0.5`, `kappa=17.0`, cutoff 12.0 Angstrom). Any alternative kernel becomes a model
selection decision and may use validation only under a documented rule.

## Paper versus public implementation

| Paper description | Public implementation | Reproducibility status | Phase-1 decision |
|---|---|---|---|
| Twelve atom-type/colored geometric subgraphs per atom | One all-heavy-atom kernel matrix and six aggregate columns | Paper representation is not reconstructable from the released code | Use the released six-column representation and label it clearly |
| Six statistics in prose; displayed equation omits median | Exactly min, max, sum, mean, median, population std | Fully defined in source | Reproduce exact order and NaN behavior |
| Covalent interactions excluded | Row-summed-radius distance mask, without bond adjacency | Source behavior reproducible; scientific intent uncertain | Preserve source mask in Phase 1; test any correction separately |
| Geometry generated/selected before learning | No public geometry-generation script or lock | Not exactly reproducible | Use the documented open-source substitute below |
| OMEGA-first geometry with RDKit/OpenBabel fallback | GGL code only requires pretyped MOL2; training only requires NPZ | Author workflow is incomplete | Do not claim exact author geometry reproduction |
| Atom-type ablations and colored-graph interpretation | No alternative colored feature mode found | Required artifacts/code appear absent | Do not infer or invent missing channels |
| BBBP and B3DB applications | BBBP, B3DB classification, and B3DB regression call the same six-column GGL implementation | Reproducible for fixed MOL2 and kernel | Use the BBBP architecture with the common six-column path |

No alternative script or configuration in the public revision implements the richer representation.
The available BBBP and B3DB paths vary model settings and chosen kernels, not feature dimensionality.
The missing items are the complete geometry-generation process, authoritative typed MOL2 inputs for
our molecules, and any code/artifacts for the paper's colored-subgraph form.

## Geometry provenance: three separate questions

### A. What the authors report using

The paper and supplement report pre-existing 3D structures for MoleculeNet BBBP. For B3DB, they
report an OMEGA-generated diverse ensemble and selection of one lowest-energy MOL2, with an RDKit
ETKDGv2-to-PDB-to-OpenBabel-to-MOL2 fallback. They do not publish tool versions, seeds, protonation
rules, OMEGA options, conformer counts, pruning, energy method, minimization limits, or atom mapping.
No public source establishes MMFF or UFF as part of the author workflow. OMEGA is commercial and is
not imported by the released code.

### B. What the released code requires

The released feature extractor requires externally generated, three-dimensional, SYBYL-typed MOL2
files. The training scripts require only their positional six-column NPZ output. OMEGA, RDKit 3D,
MMFF, UFF, and OpenBabel are not direct requirements of public training. BioPandas is the released
MOL2 parser.

### C. What this project needs

`BBB_Martins` needs a deterministic, openly specified source of one geometry and reliable SYBYL
types. Exact author geometry cannot be reproduced from the published information. Phase 1 therefore
needs an explicit compatibility substitute, with source identity and atom order controlled by
RDKit and with MOL2 conversion treated as an audited boundary rather than a source of identity.

## Candidate geometry policies

### Candidate A: RDKit ETKDG

RDKit provides explicit ETKDG versions and fixed random seeds; its documentation shows adding
hydrogens before embedding and exposes ETKDGv3, multi-conformer generation, and MMFF optimization.
ETKDGv3 is available in the proposed `rdkit<2025` compatibility range, but the final scientific
environment must pin an exact resolved RDKit build rather than rely on this broad constraint.

Recommended resolved settings are:

- parse the verified isomeric canonical SMILES without neutralization, tautomerization, fragment
  removal, or stereochemistry rewriting;
- assign a stable original heavy-atom index before any geometry operation;
- add explicit hydrogens before embedding;
- use `ETKDGv3()` with `enforceChirality=True`, `useRandomCoords=False`, `numThreads=1`, a fixed
  candidate count of 20, and all other resolved parameters serialized rather than accepted as
  undocumented library defaults;
- derive a signed 32-bit per-molecule embedding seed from a versioned hash of the preprocessing
  seed and canonical SMILES, so execution order and parallelism cannot change a molecule's seed;
- use a fixed heavy-atom RMS pruning threshold of 0.5 Angstrom and deterministic conformer-ID
  tie-breaking;
- optimize every candidate with MMFF94s for at most 1,000 iterations when all MMFF parameters are
  available; use UFF with the same fixed iteration limit only as a recorded fallback when MMFF is
  unavailable and UFF is fully parameterized;
- select the converged conformer with the lowest finite energy within the force field actually
  used, breaking exact ties by conformer ID; and
- remove hydrogens only after selection, while verifying that retained heavy atoms map one-to-one
  to the original RDKit indices.

This produces one downstream conformer, not conformer-averaged or conformer-ensemble features. The
fixed candidate set is justified by the authors' lowest-energy selection and is more defensible than
letting one stochastic embed stand for a low-energy structure. Candidate count and pruning are
project compatibility choices, not claims about the authors' settings.

RDKit's own documentation warns that conformer generation is subtle. Reproducibility means exact
within the pinned Linux environment and numerical equivalence within declared tolerances across a
second execution; it does not imply bitwise-identical coordinates across arbitrary RDKit builds or
platforms.

### Candidate B: RDKit to OpenBabel MOL2/SYBYL conversion

The current public RDKit Python API documents MOL2 reading but no supported MOL2 writer. It cannot
by itself guarantee the SYBYL atom types required here. OpenBabel supports MOL2 output and exposes
translation from its internal atom types to SYBYL types. Therefore a source-faithful Phase-1 MOL2
boundary requires a pinned OpenBabel build unless an authoritative pretyped MOL2 source is supplied.

OpenBabel must be used only after RDKit has generated and selected the geometry. Its exact input
format, command/API call, aromaticity and charge options, output format, and version must be pinned.
Conversion may alter aromaticity perception, atom names, bond orders, formal-charge records, or atom
order. It is not accepted unless synthetic golden tests prove the required SYBYL strings and allow
every MOL2 heavy row to be mapped back to the RDKit reference atom. OpenBabel is consequently
**required by the recommended source-faithful plan, but not authorized as a dependency until the
next synthetic proof task passes and the environment contract is revised explicitly**.

### Candidate C: independent typing without OpenBabel

An in-memory implementation could avoid MOL2 mathematically by combining RDKit coordinates with
independently generated SYBYL-like types. That would require complete, versioned perception rules
for at least aromatic carbons/nitrogens, planar and amide nitrogens, carboxylates, hypervalent sulfur,
formal-charge environments, and supported metals. The public repository provides a radius lookup,
not those typing rules. Reimplementing them without authoritative golden typed molecules would be a
new chemical representation and a larger compatibility deviation than a pinned OpenBabel boundary.

Candidate C is not sufficiently faithful for the initial baseline. It may be evaluated later only
against an approved collection of authoritative MOL2/type fixtures.

### Recommendation

Use Candidate A for deterministic coordinates and Candidate B for audited MOL2 serialization and
SYBYL typing. Preserve RDKit as the molecular-identity authority. Do not use OMEGA. Do not use
OpenBabel for conformer generation or optimization. Do not implement Candidate C in Phase 1.

## Critical MOL2/SYBYL contract

MOL2 is required by the released parser, but it is not intrinsic to the six mathematical features.
For Phase 1 it remains a required, hash-addressed audit artifact because it exposes the exact
coordinates and type strings supplied to the source-faithful calculation. A later validated
in-memory implementation could remove the file-format dependency while preserving identical typed
rows and numerical results.

MOL2 atom identifiers conventionally begin at one, and OpenBabel's atom API is one-based. Neither
fact proves row alignment. BioPandas preserves the atom-table row sequence it parses, and the public
GGL code uses that sequence without sorting by `atom_id`. The implementation must treat `atom_id`
as provenance only, never as the Chemprop array index.

The OpenBabel writer's exact outputs for `C.ar`, `N.ar`, `N.am`, `N.pl3`, `N.4`, `O.co2`, aromatic
bonds, and formal/partial charge fields must be covered by golden fixtures. The GGL calculation
ignores bond and charge columns, but wrong perception there can change an atom's SYBYL type. A
successful file write alone is insufficient.

## Atom-order alignment contract

The positional mapping

```text
canonical-SMILES heavy index -> RDKit heavy index -> MOL2 heavy row
-> GGL row -> Chemprop atom-feature row
```

must be proved for each molecule, not assumed.

- RDKit constructs atom indices in the parse order of the supplied canonical SMILES. Calling
  `MolToSmiles` does not reorder an already constructed molecule, but reparsing the resulting string
  creates a new molecule whose indices follow that serialized form.
- `Chem.AddHs`, conformer embedding, optimization, and hydrogen removal are expected to retain the
  original heavy-atom order, but this must be asserted against stored pre-operation indices under
  the pinned RDKit version.
- MOL2 conversion is an untrusted reorder/type-perception boundary. Neither output `atom_id` nor row
  position establishes identity.
- BioPandas returns the MOL2 atom rows in file order. Filtering exact `H` rows preserves the relative
  order of the retained rows.
- Chemprop 2.1.0's `SimpleMoleculeMolGraphFeaturizer` iterates `mol.GetAtoms()` and horizontally
  concatenates the corresponding extra-feature row. Consequently GGL row `i` must map exactly to
  RDKit/Chemprop atom index `i`.

Before conversion, assign every RDKit atom a temporary original-index token and write a sidecar
record. The conversion proof must not depend on that token surviving. Re-read the MOL2 as chemistry
and establish a one-to-one heavy-atom graph isomorphism to the RDKit reference. For every mapped atom
verify:

- original RDKit index and any surviving atom-map/name token;
- atomic number and isotope;
- formal charge;
- aromatic flag;
- chiral tag and assigned CIP label when defined;
- heavy-atom degree, hydrogen count, and sorted neighbor/bond-order/stereo signature; and
- coordinates corresponding to the selected RDKit conformer within the declared serialization
  tolerance.

Reorder typed MOL2 rows and coordinates into original RDKit heavy-atom order before GGL is computed.
Record both directions of the mapping. If graph automorphism leaves multiple mappings possible,
resolve only with a proven preserved index token and coordinate correspondence; otherwise return
`atom_alignment_failed`. A deterministic arbitrary choice among symmetric atoms is not sufficient,
because those atoms can have different geometric environments. Assert the final atomic-number
sequence, adjacency matrix, row count, and coordinate distance matrix before passing `V_f` to
Chemprop.

## Identity-bearing artifact format

Use one compressed NPZ plus one canonical JSON sidecar per molecule, with a split-level JSONL
manifest. This balances efficient NumPy loading with auditable, diffable metadata. Parquet is a poor
primary container for ragged atom arrays, and many separate NPY files would multiply filesystem
operations. Object arrays and pickle must be forbidden; load NPZ with `allow_pickle=False`.

The NPZ contains only typed numeric arrays:

- selected heavy-atom coordinates in Angstrom, shape `(n_atoms, 3)`;
- atomic numbers, isotopes, formal charges, aromatic flags, and original RDKit indices;
- MOL2-row-to-RDKit and RDKit-to-MOL2 maps;
- raw six-column GGL matrix in fixed feature order; and
- optionally the normalized matrix in a separately named field whose scaler identity is recorded.

The JSON sidecar contains at least:

- artifact schema/preprocessing version and creation status;
- molecule ID, canonical SMILES, canonical-SMILES hash, source split, source row/composite identity,
  and source development-manifest identity;
- source-row hash without the target value in geometry-derived hashes;
- exact RDKit, OpenBabel, BioPandas, NumPy, SciPy, and operating-system versions;
- complete ETKDG parameters, per-molecule seed, conformer IDs, force-field choice, convergence codes,
  energies, selection/tie-break decision, and hydrogen policy;
- MOL2 hash, coordinate unit/precision, ordered SYBYL types, ordered atom signatures, and mapping
  verification results;
- kernel index/provenance, type, `tau`, `kappa`, cutoff, radius-table hash, covalent-mask variant,
  feature names/dimension, raw array hash, and non-finite/no-neighbor flags; and
- scaler artifact/hash when normalized features are present.

The JSONL manifest has exactly one record per input row and includes successes and failures. It
records expected/observed counts and hashes and permits completeness checks without opening every
NPZ. JSON is serialized with fixed key ordering and numeric/text conventions; hashes cover schema,
metadata, and raw array bytes independently. Geometry/MOL2/NPZ caches are large run artifacts and
must remain uncommitted unless explicitly intended.

## Deterministic failure policy

No molecule is silently dropped, no fallback changes molecular identity, and no split is rewritten.
The preprocessing command first emits a status for every requested molecule and fails the scientific
run if any blocking status remains.

| Condition/status | Deterministic action | Phase-1 disposition |
|---|---|---|
| `success_mmff94s` | Use lowest-energy converged MMFF94s candidate | Accept |
| `success_uff_fallback` | Use UFF only when MMFF is wholly unavailable and UFF is wholly parameterized | Accept but report/count separately |
| `parse_failed` | Record RDKit error and identity; do not rewrite SMILES | Stop |
| `hydrogen_addition_failed` | Record exception and atom signature | Stop |
| `disconnected_fragment` | Do not select largest fragment or reposition fragments silently | Stop for an explicit scientific decision |
| `embedding_failed` | One fixed-seed ETKDGv3 run with the resolved candidate settings; no changing seeds until success | Stop; retain diagnostics only |
| `mmff_unavailable` | Attempt the predefined UFF fallback | Continue only if UFF succeeds |
| `uff_unavailable` | Do not invent parameters or retain arbitrary coordinates | Stop |
| `optimization_failed` | Reject nonconverged candidates; if none converged, retain coordinates only as diagnostics | Stop; do not featurize them |
| `mol2_generation_failed` | Retain the approved RDKit artifact and converter logs | Stop |
| `unsupported_atom_type` | Report atom index/type; do not rely on source NaN omission | Stop |
| `sybyl_typing_failed` | Report expected chemistry/signature and observed type | Stop |
| `atom_alignment_failed` | Retain both signatures and candidate mappings | Stop |
| `ggl_failed` | Record kernel/configuration and numeric error | Stop |
| `no_retained_neighbors` | Preserve source raw NaNs/sum-zero, record flag, then allow documented Chemprop zero-fill | Accept only when all atom types are supported |

An explicit-hydrogen single-heavy-atom molecule can legitimately have no retained heavy-atom
neighbor. That source-defined case is distinct from an unsupported type. Any real-data failure
policy change requires a reviewed configuration version; validation performance must not choose it.

## One-conformer contract

The public extractor assumes exactly one MOL2 geometry per molecule and emits no conformer axis.
Phase 1 will likewise provide exactly one selected geometry. It will not average features, choose a
conformer using labels, or ensemble conformers at training/inference. The fixed 20-member ETKDGv3
candidate set is only a deterministic search from which one lowest-energy conformer is selected.

## Leakage and normalization

SMILES parsing, hydrogen addition, embedding, optimization, type assignment, atom mapping, and GGL
calculation depend only on molecular structure and fixed configuration. They never receive targets.
Train and validation may be generated independently or in parallel because the per-molecule seed is
identity-derived and the algorithm is identical.

After all raw GGL matrices pass integrity checks, construct Chemprop training datapoints first and
call `train_dataset.normalize_inputs("V_f")`. Chemprop concatenates all training atom rows and fits a
scikit-learn `StandardScaler` independently across the six columns. Apply that same scaler object to
validation; never fit or refit on validation. Serialize feature order, mean, variance, scale,
training molecule/atom counts, input hashes, and scikit-learn version. Validation labels do not
influence geometry, GGL, kernel settings, scaling, failure handling, or artifact acceptance. No test
path is accepted by this preprocessing entry point.

The tolerances are initial acceptance bounds to validate empirically under the pinned Linux
environment, not permission to weaken checks until unstable output passes. A third test should alter
the seed and demonstrate that provenance/hash changes. No BBB molecule or label is used.

## Chemprop 2.1.0 interface

The released scripts construct a `MoleculeDatapoint` with `V_f` shaped
`(number_of_RDKit_atoms, 6)`. Because the molecular graph is created without explicit hydrogens, this
is the number of heavy atoms. `MoleculeDatapoint.__post_init__` converts `V_f` NaNs to zero.

`SimpleMoleculeMolGraphFeaturizer(extra_atom_fdim=6)` declares the additional dimension. It creates
the ordinary feature matrix by iterating `mol.GetAtoms()` and then performs a horizontal
concatenation with `V_f`; the extra values therefore enter **before message passing**. Chemprop
2.1.0's default v2 ordinary atom features have dimension 72, so the model's atom input dimension is
`72 + 6 = 78`; the ordinary bond dimension remains 14. The source passes that 78-dimensional
`atom_fdim` to `BondMessagePassing`.

Chemprop does not automatically normalize extra atom features during featurization. The upstream
script explicitly invokes `normalize_inputs("V_f")` on the training dataset, receives the fitted
scaler, and passes it when normalizing validation. Chemprop implements this by concatenating all atom
rows, fitting or applying a `StandardScaler`, transforming each molecule's matrix, and rebuilding
its mol-graph cache.

These behaviors are visible in the tagged Chemprop 2.1.0
[`MoleculeDatapoint`](https://github.com/chemprop/chemprop/blob/v2.1.0/chemprop/data/datapoints.py),
[`MoleculeDataset`](https://github.com/chemprop/chemprop/blob/v2.1.0/chemprop/data/datasets.py), and
[`SimpleMoleculeMolGraphFeaturizer`](https://github.com/chemprop/chemprop/blob/v2.1.0/chemprop/featurizers/molgraph/molecule.py).

## Decision gates

1. **Can the public GMC-MPNN BBBP representation be reproduced from available source?** Yes, for
   fixed typed MOL2 input and a resolved kernel: the released six-column calculation is sufficiently
   specified, including its surprising mask.
2. **Can author geometry be reproduced exactly?** No. Inputs, versions, seeds, and complete
   OMEGA/RDKit/OpenBabel settings are absent.
3. **Can a defensible deterministic open-source replacement be built?** Yes: pinned ETKDGv3,
   explicit force-field convergence/selection, audited OpenBabel typing, and identity-bearing
   artifacts.
4. **Is OpenBabel required?** Conditionally yes for the recommended source-faithful Phase-1
   MOL2/SYBYL boundary. It is not a training dependency and must first pass synthetic golden tests.
5. **Is MOL2 required?** Yes for direct compatibility with the released parser and as the Phase-1
   audit boundary; no for the kernel mathematics in principle.
6. **Can SYBYL typing be reproduced reliably?** Not with RDKit alone. It is plausible with a pinned
   OpenBabel version, but reliability remains gated on explicit aromatic/amide/charged golden tests.
7. **Can atom order be guaranteed?** Yes only through stored atom identity, graph-isomorphism and
   coordinate checks, explicit row reordering, and a fail-closed ambiguity policy—not by positions.
8. **Are six GGL features sufficient for Phase 1?** Yes. They are the only reproducible public
   BBBP path and must not be represented as the unreleased richer colored representation.
9. **Largest remaining risk:** SYBYL type and atom-identity fidelity across RDKit-to-OpenBabel-to-MOL2
   conversion. Geometry non-equivalence to the authors is an unavoidable declared compatibility
   deviation; silent type/order drift would be a preventable invalidation.
